# Source release readiness

Reviewed 7 September 2026. This gate covers a source archive generated by
`git archive`; it does not cover a local evidence directory, MP snapshot,
candidate-level ranking bundle, dependency environment or production Seko
database.

## Ordered pre-tag checklist

Run this checklist from the repository root. The candidate is the exact commit
printed in step 1; do not tag it if `HEAD` changes, the working tree becomes
dirty, or any later step fails. Start again from step 1 instead.

1. Freeze and identify the candidate:
   ```bash
   git status --short
   git rev-parse HEAD
   git branch --show-current
   ```
   Require an empty status and the intended release branch. Record the full
   commit SHA in the release notes.
2. Run the Julia package gate:
   ```bash
   julia --startup-file=no --project=. -e 'using Pkg; Pkg.test()'
   ```
3. Run the Python gate:
   ```bash
   python3 -m unittest discover -s test -p 'test_*.py'
   ```
4. Audit the archive made from the candidate commit, retaining the audit outside
   the repository:
   ```bash
   candidate=$(git rev-parse HEAD)
   python3 scripts/verify_release.py --archive "$candidate" --output /tmp/eka-release-audit.json
   ```
   Require `"status": "pass"` and an empty `problems` list.
5. Push that commit and require every job in its GitHub Actions run to pass,
   including Documentation. Confirm that the development manual is reachable at
   `https://JoshCCorby.github.io/EkaCompositions.jl/dev/`.
6. Immediately before tagging, repeat step 1 and require the recorded SHA and
   clean status to be unchanged. The tag must point to that SHA.

Ignored local data and evidence directories are not members of the archive.

## Archive gate details

The audit builds the actual Git archive and fails on:

- local data, report or activity-log paths;
- unreviewed JSONL/SQLite/database files, except the documented tiny fixture;
- environment files and `Manifest.toml`;
- symbolic links, hard links and other special archive members;
- private-key markers and common GitHub, AWS and literal MP API-key forms;
- machine-specific home paths, files over the review limit, missing licence,
  notice/citation metadata, or absent MP/Seko attribution.

The JSON output records every regular archive member's type, mode, size and
SHA-256 plus a manifest hash. It is a content-control aid, not a guarantee that
arbitrary secrets or all legal issues can be recognized automatically. CI runs
the audit and its focused tests on every push and pull request.

## Terms and decision

The [terms evidence](mp-terms-evidence.md) now includes a read-only check of the
live official MP page on 31 August 2026. That page confirms CC BY 4.0 for MP
Content with credit, licence link and change indication, and separately assigns
GNoME CC BY-NC 4.0. The project excluded GNoME. MP asks users to contact it for
guidance before repackaging and publicly redistributing MP data.

The source-only archive is ready as a release candidate because it does not
repackage record-level MP data and retains the relevant attribution and notices.
No tag, GitHub release or data publication is performed by this review. A future
MP data/results bundle must receive a separate file-by-file review and may warrant
provider guidance based on its concrete contents.

## 0.1.1 candidate scope

Version 0.1.1 applies this same ordered gate after adding reproducible code and
synthetic tests for the subgroup, system-concentration and 20,000-iteration
stability diagnostics. Its release notes explicitly describe a reproducible
ranking benchmark rather than a validated discovery model. The tag and GitHub
source-only release must identify the exact candidate SHA; that external record
avoids the impossible self-reference of embedding a commit's own SHA in the
commit. No data, rankings, factors, environment or other evidence asset is to be
attached to the release.
